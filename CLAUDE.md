# Working in this repository

`CONTRIBUTING.md` owns the process; this file is the short form a session reads first. Where the two disagree, CONTRIBUTING wins and this file is fixed.

## What to do, in which order

The order of work lives outside the tree: the maintainer keeps a plan under `docs/plans/` (git-ignored) and a memory note that holds the current ordered steps. Read those before choosing a task; do not infer the order from the git log. A session covers the tasks its plan assigns and stops at the boundary the plan names, even with context to spare; at the stop it commits, rewrites the memory note's current steps in place, hands over any push, and says whether a fresh session can continue from the files alone.

## Commits

- One workstream per commit; a change that would be reverted separately is a separate commit. Subject is the outcome, body is the mechanism; no session narration, no attribution trailers.
- **A backlog entry is committed by the session that writes it, in a commit of its own, as soon as it is written** — the queue line in `BACKLOG.md`, or the move that files one under `backlog/`. The commit body carries the observation behind the entry, which the one-sentence entry cannot; and an uncommitted entry is a stray change every later session has to explain or step around.
- A skill, agent or brief edit that changes behaviour is tested before it lands (CONTRIBUTING, "Testing a wording change"): a baseline that fails, one wording, five fresh sessions per arm - twenty where the rule is one of restraint, since that baseline is taken on the strongest model too - every grader of the case in both arms, the result written into the case's `results/manual-run.md`. A wording that costs a neighbouring grader is declined with its reason, not reworded a third time on the session's own judgement.
- The version bump goes in the commit that changes behaviour; a bumped manifest releases on push.

## Backlog

- **A new entry starts with a search, not with a line.** `grep -rin` the mechanism — two or three words of what goes wrong, not the words an entry would have used — over all three files, `BACKLOG.md` **and `backlog/`**, because the queue is in the first and everything that has left it is in the other two, and a search reaching only the queue writes a new line for a mechanism already filed. A hit in the queue takes a sighting in that entry's parenthetical instead of a second line; a hit in `backlog/parked.md` moves that entry back to its tier with the new circumstance, already carrying two; a hit in `backlog/declined.md` is the answer to the line rather than a reason to write it. Only a session that hit the mechanism itself adds a sighting; an entry carrying no count stands at the one sighting that queued it, so the first sighting added makes two.
- Recurrence is the promotion filter: two sightings — other work or another place, never the same failure met twice in one pass — or one sighting whose failure was measured - a rate, a run, or a failure that landed and whose cost the entry names, never a near miss caught before it cost anything - is what makes an entry worth a wording round, and an entry that has reached neither by the time a round reads it is parked into `backlog/parked.md`, keeping its sentence and naming what a second sighting would be, which is a finding about the mechanism rather than a decline. `BACKLOG.md`'s header carries the shape, CONTRIBUTING's "Where a lesson waits" the reasoning.

## Review

Most changes here are verified by something stronger than a reading before they land: wording-tested contracts, grader patterns tested on captured runs and scored by the runner, fixtures built under a hostile global git config. Do not re-review those. Review the prose that loads into sessions — `hooks/session-brief.md`, `skills/*/SKILL.md` and the references they point at, `agents/*.md`, `CONTRIBUTING.md`, `README.md`, and `CLAUDE.md` itself, which loads automatically into every session here and is therefore the least reviewed and the most obeyed — as one doc-vs-code pass over its diff: each changed sentence against the file it cites and its neighbouring copies (brief core against skill, agent contract against owning skill, a reference against the SKILL.md clause that points at it, README paraphrase against skill, this file's short form against the CONTRIBUTING section it compresses). Run records and the backlog's entries carry no behaviour and are not reviewed — but the headers of `BACKLOG.md` and the two files under `backlog/` are instruction prose a session obeys at intake, and the range below leaves all three out, so those headers are read in the same pass from a diff of their own (`git diff prose-passed..HEAD -- BACKLOG.md backlog`). Shell under `scripts/` and `evals/fixtures/`, and any eval case never run in both arms, get an ordinary review.

**The range is the watermark, not the last push:** `git diff prose-passed..HEAD -- hooks skills agents CLAUDE.md CONTRIBUTING.md README.md`, where `prose-passed` is a lightweight local tag marking the commit through which this prose has actually been read. The pass is its own unit of work, never started inside a task; it is due at about 150 changed lines, at a push whatever the size, or after two task units; and it closes by moving that tag to the head it read, which is its only durable output (CONTRIBUTING, "Before pushing", has the mechanics and why a push is the wrong anchor).

Findings files (`review-findings-*.md`) are point-in-time and git-ignored; delete one once everything in it is closed or carried into the plan.

## Gates

The eight local gates are the steps of `.github/workflows/guard.yml` minus the skills-spec validator, which is not installed locally; run them at the head before handing over a push. The local shellcheck is newer than CI's, so a clean local lint does not prove CI's lint step.

## Evals

- `evals/results/` is git-ignored and holds the baseline JSON of each release; the runner keeps each run's findings file or reply as grader `evidence` in that JSON, which is what to hand-grade when a judge verdict looks wrong. The judge is unreliable on long files, on findings renumbered at a merge, and on a case whose graders are many tone rubrics over one document — there it over-fails both arms and unevenly, so the difference between them is no safer to read than the rate, and a row is hand-graded in both arms before any decision rests on it.
- `scripts/eval-trend.py` folds those kept runs into one row per case, grader and release, which is the whole key a wording round's two arms share: copy a round in as `<round>@baseline.json` and `<round>@<wording>.json` — the only thing that keeps a declined wording out of the release's own trend — and read a `!` on a row as one version folded from two plugin checkouts, which the fold cannot tell apart.
- A new grader is mechanical — `regex`, `file_exists`, `tool_used` — unless its condition is irreducibly semantic; but a pattern anchored in a string the fixture seeded scores whether the run edited the draft rather than whether it did what the rule asks, and passes in both arms once that wording is softened. Anchor it in what the run must produce, and leave a rubric about what the run writes instead, and where, to a judge.
- A git act inside the eval sandbox runs on the git the scaffold puts there: every case's `fixture.sh` calls `evals/fixtures/stage-git.sh`, which writes a wrapper into the run's own home and a `.zshenv` putting it first, and **a new case is not finished until its scaffold carries that line**, whether or not its graded act is a git command. The sandbox's own `git` is a stub that dies writing its cache, and the working binary loses the PATH search from any position, being a symbolic link into a tree the sandbox will not let the shell stat - so prepending its directory changes nothing and the failure reads as a PATH order problem it is not. Without the line the split is silent and lands as a grader rate: seven reps of ten found the absolute path in the round that measured it while three escalated the act as blocked, which fails the act's grader and any grader reading the list it belongs on - unusable for that round rather than failed - and ten of ten performed it on the re-take. Settle a question about a run's environment from what a run keeps: `--keep-temp` leaves the run root, whose `config/settings.json` is the sandbox policy and whose trace holds every command a rep ran, and a case file's `execution.env` takes `EVAL_*` keys only, everything else coming from the operator's shell or the scaffold.
- A file-targeted grader whose target is absent throws and is scored a fail, `not_contains` included; a behaviour that legitimately deletes a file cannot be graded through that file. `focus` and `target` take one literal existing file — no glob, no directory — so a grader reads only a path fixed before the run: the case prompt names it, or the grader reads the index that points at it. An `llm` grader with no `focus` is shown the run's final message alone, and a `file_exists` grader reads the run's own file changes rather than the tree (CONTRIBUTING, "Testing a wording change", has the five rules).
- A `tool_used` grader's `input_match` is tested against the call's whole input JSON — `Bash`'s prose `description` and any comment the command carries included — so a pattern on a bare identifier scores a call that changed something else as the act, and a heredoc or a `Write` carrying the whole file reads an untouched line as the act applied. Anchor on the transformation: the replaced text together with the line that replaces it, or a whole body written without the part the act removes. The tools it does not name are a blind spot its arms need not share — the rule under test chooses the tool, and a wording asking for every row one at a time moved six reps of ten onto `Edit`, where the `Bash`-anchored grader read 4/10 against a hand-read 10/10 — so keep a companion grader per tool, read those rates across the arms, and hand-read the draw of every rep one of them fails, which needs `--keep-temp` because the runner deletes each run's workspace.
- A `tool_used: Skill` grader marked `arm: with-only` is the trigger's own indicator: scored in neither arm, never evaluated in the arm without the plugin, and the only thing that separates "the skill never loaded" from "its rules did not hold". A skill whose condition is a standing rule rather than a named task is never reached through that tool at all - 59/59 on the cases whose prompt names work the skill owns against 0/13 on the two whose skill fires on how a message ends - and the brief reaching the model is a different event that does not imply it. So a rule living in such a skill's body cannot be moved by any round the runner can buy: read the indicator before designing the arms, and either restate the rule to land where every rep does read or do not buy a runner round for it.
- The runner's `--case` filter takes one `*` glob.
- The default judge fails conditions that a hand read and a stronger judge both pass, on a multi-condition rubric over a file of a few kilobytes — measured against hand labels on two kept findings files, where it agreed with five of eight cells and the stronger judge with eight of eight. The judge is chosen once per invocation and no grader file can name one (`model`, `judge_model`, `judge-model` and `judgeModel` are rejected at load), and that choice is settled rather than open: pass `--judge-model sonnet`, $2.00–3.50 more on a baseline upwards of $55 (`evals/judge-calibration.md` has the cells). One condition per grader and a hand grade from the run JSON's `evidence` stay worth using on their own merits, not as substitutes for it.
- A curtailed rep is unmeasured, never a fail, and is replaced rather than counted - but why it curtailed is a finding: a rule that asks for more work costs more turns, and one rep in five crossed a case's 60-turn cap under a wording that prices the work it asks for. Read both arms' turn and duration spread before any grader, and where the treated arm sits near the cap, raise the case's limits in both arms and re-take. Likewise, a rubric's rate is not comparable across two readings where a wording changed how much the run writes about what that rubric judges: one held 4/5 on a baseline and 0/5 under a wording that made each rep write a per-row verdict list, on files that affirm those rows by name. Nor across a repair to the instrument, where the move can be the judge's alone: one held 10/10 before the sandbox's git was staged and 5/8 after, on the same model, rubric and judge, with a hand read passing both sides in full - and the ready-made cause, that a working git let the reps re-apply mutations and write verdict language beside the record, is refuted by the runs before the repair, which reached a working git by the binary's full path, re-applied the same row, and wrote the same language in files the judge passed; so across a repair, test a cause for the move against the side the repair had not reached before writing it down. Hand-grade such a row rather than reading its rate, on both sides of the change whichever way it moved, and say so in the case's record.
- The instrument has a floor: five reps an arm separate the arms only on a four-in-five gap, ten only on a half, and a three-rep baseline row only on a clean sweep — so a rule whose expected effect is one run in five or fewer is restated to bind every run, or declined as below the instrument, never measured harder.
- Before that floor, check that a rep reaches the condition the rule fires on: a rule carried by a trigger no rep crosses is untestable by this instrument rather than unproven, and where staging that condition means changing the fixture in the one way that removes it — shrinking the window a rule about remaining room would be measured against — no wording can be read out of the round, since both arms score alike for a reason having nothing to do with it. A condition no rep reaches on its own may still be stageable, and what answers that is the case format's own inputs rather than the kept traces, which show only whether the condition has occurred: `context.history_file` seeds a prior conversation by resuming a transcript the case ships, so a rule about what a second message must do is reachable although every case here is a single prompt — a rule whose condition the format can seed is untested rather than untestable, short a fixture rather than short a verdict.
- A replay case's seeded conversation carries the always-on brief itself, since the start hook does not fire on a resume, and the one run of such a case under `with-without` reported a single arm - no ablation row, so no retirement signal either way. The seeded copy is frozen at generation, and the first replay run showed the skill's text is not live to the reps either, none of them having called the Skill tool - so a replay round tests a brief wording and regenerates the fixture once per arm, each arm's seeded copy carrying its own text, with a regeneration that finds no diff as the staleness check.
- A rule about restraint (what a session must not do) needs its baseline taken on the strongest model the maintainer runs as well as on the eval instrument: the stronger model over-applies a rule it has understood, and the weaker one may never have exhibited the failure.
- A row whose no-plugin arm scores as well as its plugin arm is a retirement flag, not a result: three things produce it — a grader that passes without the behaviour, a row with no rule behind it, and a rule the model has internalised — and only the third is a retirement, confirmed by running the landing test backwards (CONTRIBUTING, "When a rule outlives the model that needed it").
