# Backlog

Mechanisms learned in real work that have not yet been re-derived into a
skill. Each entry is one sentence with no proper nouns — what goes wrong and
why — and names the skill it is aimed at. This file is the queue; two files
beside it hold what has left the queue, and all three are one search at
intake:

| File | What it holds |
|---|---|
| this one | the queue — what a round can still take up |
| [`backlog/parked.md`](backlog/parked.md) | met once and not since; keeps its sentence, and names what would make it two |
| [`backlog/declined.md`](backlog/declined.md) | answered rather than awaited — tested, measured, or outside the skills; its preamble has the grounds |

An entry leaves the queue in the commit that promotes it (re-derived per
CONTRIBUTING, never pasted), parks it or declines it; a parked or declined one
keeps its line in the file it moves to, so the same lesson is not queued twice,
while a promoted one keeps none and lives in its skill. A review-pr or
agent-contract change runs the wording test first, and a baseline that
already passes means decline, not land.

**Before writing a line, search all three files for the mechanism** — a search
that stops at this one writes a new line for a mechanism already filed, which
is the failure the split exists to avoid:

    grep -rin '<word>' BACKLOG.md backlog/

run once for each of two or three words of what goes wrong, rather than the
words an entry would have used, because the same defect arrives described
differently every time; read a doubtful match in full. What a hit means
depends on where it lands, and each of the three has its own action.

**A hit in the queue below** — add a sighting to that entry, in the
parenthetical it already carries, instead of a second line; each sighting is
its own circumstance, held to the same bar as the sentence:

    … → review-pr, grading (2 sightings: a record of four rows where a draw
    of three skipped the contradicted one; a review whose sample stopped at
    the opening entries of a nine-row record)

A sighting is added only by a session that hit the mechanism itself — agreeing
with an entry is not an observation — and an entry carrying no count stands at
the one sighting that queued it, so the first sighting added makes two.

**A hit in `backlog/parked.md`** — move the entry back to its tier here with
your own circumstance added. It arrives carrying two sightings, which makes it
eligible for a round at once.

**A hit in `backlog/declined.md`** — read the reason rather than writing the
line; it is the answer to the entry you were about to queue, and where a
decline is re-openable that entry says so and on what.

**Two sightings, or one sighting whose failure was measured, is what makes an
entry worth a round.** Met once it is a hypothesis; the second sighting — other
work or another place, never the same failure met twice in one pass — is the
evidence the first one lacked. Measured means a rate, a run, or a failure that
landed and whose cost the entry names; a near miss caught before it cost
anything is a sighting, not a measurement. An entry that has reached neither by
the time a round reads it moves to `backlog/parked.md`, which is a finding
about the mechanism and not a defeat: it keeps its sentence so the search above
still matches it, and ends with what a second sighting would be. Declined is
the other outcome and a different one: the entry has been answered rather than
left waiting, so an effect measured and found too small for the instrument to
separate is declined on that ground and never parked — parking is for what is
untested and short a sighting. `backlog/declined.md`'s preamble names the
grounds a decline can rest on; CONTRIBUTING's "Where a lesson waits" has the
reasoning.

Nothing here is pre-approved; the tiers are the maintainer's current read of
what a rule would be worth, and the sighting count is what says it is ready to
test.

## Strong — prevents a real failure, general

- A check that could not have passed whatever the work did — its input absent, its budget spent, its evidence in a place it cannot read — is unmeasured rather than failed, and a tally that counts it as a failure reads as a regression the work never caused; ask of every failing check whether a correct run could have passed it, and lift the ones that could not out of the count before reading the result or writing it down. → implementation-gates, Gate 3 (its family's round did not land and never reached this entry's own half: on three cases built for the general sentence it would have been promoted under, no run met a check that could not have passed, so the entry is untested, and a round on it needs a case where a check fails for a reason the work cannot affect - its input absent, its budget spent, its evidence out of its reach; 3 sightings, all measured, the first two circumstances below from one round: confirmed on a batch of six measured runs whose table read as a clean no-difference result: one real verdict sat under five non-verdicts, three whose input file did not exist and two whose paid checks were skipped at a spending ceiling; separately, a check whose rubric described a written document but whose input was the worker's summary of it voted three times against a document that satisfied the rubric in full; and again where a check read the work's own list of changed files rather than the tree, so a file the setup had placed and the work correctly left alone was reported missing and failed every run in both arms; and again where the tool running a batch refused its own working directory before the work began, so seven runs of fifteen produced no turns, no output and no trace and were each scored zero inside the batch's headline rate, which a reader taking that rate at face value would have read as the work collapsing)
- A forge's comment API can answer a successful create with JSON the spec would reject — literal control characters and under-escaped backslashes inside the comment body it echoes — so a strict parser raises on a post that fully landed, and the error output is indistinguishable from a failed post; the posting script keys success off the response status and parses the body leniently, and any retry lists the existing threads first, because the obvious reaction to the error doubles every comment. → review-pr, posting reference (untested; eight of eight creates succeeded while every parse raised, one of them on a backslash the suggestion block itself introduced)
- Compact packing merges findings by defect class, and that merge may not dissolve a partition the findings already carry. Two of them bind: membership of the change's own file set, because one merged thread demotes its in-diff members to change level and each loses the anchor that is the only thing taking the reader to the line; and a group already formed in the default list, because re-packing by class tears apart items that are one contiguous edit to one region and the single appliable block the grouping existed to preserve is lost. A class whose members straddle either partition becomes two threads, and the rule that merges block-carrying findings applies to separate findings, never to the members of one group. → review-pr, the compact section and its posting reference (untested; one sighting, whose failure landed: a three-member thread posted at change level carried an in-diff finding whose anchor was the only way to the line it was about, because the other two members sat outside the diff and shared its class - the demotion shipped to the author unremarked, while the second circumstance of the same pass, a formed group torn apart by re-packing, was caught during assembly and never posted)

- A contrast-threshold accessibility scan is directionally blind, not merely threshold-blind: on a light surface a darker foreground can only raise the ratio, so such a scan can never flag a lighter-to-darker change or its revert, which makes "the scan reaches this element" and "the scan would catch this change" two different claims — ask which one a coverage credit rests on. → review-pr, absence claims (untested; the scan did reach the changed element and still could not discriminate, measuring 6.4:1 before against 13.1:1 after with the rule's threshold at 4.5:1, so a revert produces no violation ever)
- An assertion can be tautological with respect to the very artifact it appears to check, because a test framework may substitute a stub for that artifact's import: consumer and test then read the same generated value, so the assertion still passes with the artifact emptied or the key absent from it — ask what the framework puts in place of the import at test time before crediting such an assertion, and read every mutation confined to that file type as unmeasurable by construction rather than as a test-quality gap. → review-pr, test-quality axis (untested; a stylesheet-class assertion passed with the class absent from the stylesheet entirely, the substitute returned a plausible hashed name for a wholly invented key, and the framework's own source comment stated that the file's contents are blanked before the substitute is built)
- A mutation's outcome is read off the failing test's own title, never off a tally or the absence of a failure line, because both go quiet for reasons that have nothing to do with the mutation: where the baseline is not green, a genuine failure takes the known-flaky test's slot and the tally comes back byte-identical to the baseline, and where the runner's reporter is not the shape the parser expects, "nothing failed" and "nothing parsed" are the same output — so a run cleaner than the baseline is not a signal either, and a parser reading the wrong format must fail loudly rather than report every run clean. → implementation-gates, Gate 1 (untested; 2 sightings: two genuine kills in one sweep each reported the baseline's exact tally and exit status while four real survivors ran cleaner than it; and a harness verifying nine mutations parsed for one reporter's failure lines while the runner emitted another, reporting no failing test on all nine, seven of which had killed exactly the test they were meant to)
- A promoted rule's trigger names something readable in the artifact it governs — a field, a heading, a marker already present — because a trigger phrased as a category the reader has to judge is one the reader can decline to apply, and the rule's justification then never fires however squarely it answers the objection the rule was written for; state the trigger as what the artifact is, not as what it counts as. → maintaining-project-memory, the promotion section (tested; one shape whose trigger was a judged category left its grader at 7/10 → 8/10 while both surviving failures answered that the category did not apply, and the same rule with its trigger restated as the artifact's own marking scored 10/10, ten reps an arm; and on the writer's side the sentence moved nothing: carried in the always-on summary and in full in the promotion section, it left sessions asked to write a rule the requester scoped by a judged category keeping that category in five of five, as five of five did without it, in a repository whose own description names the directory the category covers - three of the five had the section's full sentence loaded before their one write, and the closest any came was listing the category's instances, still a category the reader judges; a further round waits on a restated wording, drafted in a strong-model session, since the tested one moved no writer even loaded)


- A heading that states a count is an unverified claim about the body beneath it, and prose carries a wrong one indefinitely while a numbered list contradicts its own heading on sight; recompute every self-describing count from the artifact before the text leaves, and number a countable set rather than describing it. → verifying-before-sending (3 sightings: a heading stating a count that the numbered list beneath it contradicted on sight; and a table of counts derived by hand from a run's kept traces and published as that round's result, whose deciding row was wrong in one cell of five - the act it counted had been performed by writing a whole file rather than by rewriting a line, so a parse looking for a rewrite found nothing to count - caught afterwards by re-deriving the same counts mechanically from those same traces, by which time the wrong figure had been read as the reason to buy the next unit of work and had priced it; and a third of that same shape, where the count was derived from the cause rather than from the artifact - how many of a stopped run's checks carried a verdict no run could have earned was read off the fact that it wrote no output file, where three of its eight had in fact scored the work it did before it stopped - and the figure then rode into the instruction file that governs the next round, where it read as nothing in such a run being readable at all; the half of this sentence about a count that rots afterwards is the durable-prose entry's second sighting)
- A check's result is read as the sentence it prints rather than as the question it asked, so one that derived its population from the copy in hand reports a clean run at the moment the defect it exists for is being created elsewhere, and nothing distinguishes that from a real pass: a result names the scope it covers, a baseline that can be stale reports how stale it was, and a check that cannot separate two causes says so instead of naming one. → implementation-gates, what a passing gate licenses (tested in one round on three cases and not landed, because the baseline already did what it asks: with a docs gate that reads only tracked files beside two new untracked pages, one linking a page that does not exist, ten runs held the gate's clean result and nine named what it had read, made it read the new pages unprompted and reported the broken link, each having read the check's source before trusting it, while a third case's five runs never ran the gate and checked the pages by hand; so every run could see what the check covered, and a further round is worth buying only on a case where establishing that costs something - a population another system or branch holds, a cache, a rule inside a tool - which is where four of the five sightings below happened; 5 sightings, the first measured and landed with its cost, its two same-pass shapes not counted: a duplicate-identifier check derived its set from the working copy and reported zero duplicates while a parallel branch held the same identifier already, the collision surfaced four days later at a merge and cost a hand resolution across five files plus renumbering eight further identifiers; the same repair then produced the shape twice more, a replacement check printing a conclusion its evidence could not separate from an innocent edit, and the same check reading a cached remote reference while reporting a next-free value as current; and a reference-integrity gate whose population is the tracked set printing every link resolved while the files the change added, not yet staged, were the only ones whose links were in question - the same clean sentence before and after they entered the set, so the run that mattered was indistinguishable from the one that covered nothing; and twice more in real use: a platform's dependency alerts stayed silent for two months over a repository in which an audit run in the same pass found vulnerable transitive packages, none of which the alerts had raised - the silence read as "nothing vulnerable" when its population had never reached those packages; and a development server's liveness probe, clean console and green status all passed while it served the pre-edit version of a changed module, which only fetching that module twice, once with its cache defeated, separated from a live change; and in a review, a whole-page accessibility scan already in the suite was about to be credited with covering a state that a proposed new scan would cover, while it had been taken with a modal dialog open, which marks the rest of the page inert - and the scanner skips inert content in every rule, so its clean result covered almost nothing behind the dialog, found only because the question was whether the new scan duplicated it)

- An instruction in a dispatch brief that the agent's own tool set cannot carry out does not fail: nothing checks a brief against the tools the role holds, so the agent completes the work and falls back to returning it the one way it can, and where the instruction existed to prevent a failure mode that fallback is the failure mode — a report told to go to a file so it would not be truncated in a reply comes back in the reply, truncated, and the coordinator pays a second time to re-request work already done. Read each instruction in a brief against that role's tools before dispatching, and where a role's contract requires it to produce an artifact, give the role the tool rather than the instruction. → delegating-to-subagents, the dispatch brief, and the agent contracts that state what a role must produce (one sighting whose failure landed and whose cost is nameable: four agents in one pass were each told to write a report to a named path, none held a write tool, all four produced full reports that reached the coordinator only as replies, every one truncated mid-finding, and the re-requests cost eight to ten extra round trips carrying content that had already been generated once)
- Granting a role the tool its contract requires removes the impossibility, not the fallback: handing back is itself an act of reporting, so a role holding a write tool and given its report's path in the brief still returns the work in the reply, and the truncation the file rule exists to prevent arrives with nothing left to blame it on — the grant is what makes such a rule executable, never what makes it hold, so a delivery rule is read from what the replies carried and not from the provisioning. → delegating-to-subagents, the dispatch brief, and the agent contracts that state what a role must produce (untested; one sighting, taken as the grant landed: across seven dispatches of two such roles six wrote the file and one, holding the tool and given the path, wrote nothing and handed the whole report back, while one reply of the seven was the bare path the contracts require and the other five carried a verdict digest or a finding count beside it — the same reflex in its smaller form, and one a coordinator can act on instead of opening the file)
- A rule that has to fire on every unit of work cannot be delegated to a document the reader must decide to open, because nothing in the work announces the moment to open it: the reader meets a task, not the rule's condition, so a pointer naming the document and saying to consult it when the condition arises is read as description of where the rule lives rather than as an instruction to go and get it. - A ground-truth check that runs a primitive in isolation settles the primitive and not the claim, because the code runs a sequence whose earlier steps change what the later one sees — a stage-all before a commit marks every conflicted path resolved with the markers inside it, a branch name that resolves only on a remote turns a create-branch flag into a checkout of that branch — so a row marked verified can be false for the exact call the design rests on; - A check keyed to a literal the input seeded — a heading, a word, a phrase the work is expected to remove — scores whether the work edited that string and not whether it did what the rule asks, so it passes for the wrong reason while the seeded wording lasts and passes for treated and untreated work alike the moment the input is reworded, with nothing in its output to say it has stopped measuring; anchor such a check in what the work must produce instead, and where the rule is about what stands in place of the seeded text, or where it stands, no literal reaches it and a judgement is the honest instrument. → implementation-gates, Gate 1 (untested; 2 sightings, neither landed: four such checks agreed with a hand reading on all twenty-four cells where a literal existed, against fifteen for the judgement they would have replaced, and every one of the four keyed on a string the input seeded and the same record already plans to soften; and, in another repository, a check that a shared bundle carried no project-specific content was run as a search for the phrase the edit had just removed, and came back clean while the same content sat elsewhere in the file in other words and under a differently-cased prefix - there the literal came from the edit rather than from a seeded input, which is the same check measuring the string instead of the property the change was meant to establish)

- A claim that a message was sent reads as corroborated once the documents summarising the work repeat it, although every copy descends from one summary, and a message handed to someone else to send has no confirmation loop: a send that never happens reports nothing, so the default reading becomes "sent". Record such an item as drafted until the artifact the message would have changed shows it, and check a sent claim there - the note it would have amended, the thread it would have appeared in - never in another document repeating the claim. → verifying-before-sending, beside the absence traps, as their presence-side counterpart; the ledger half is tracking-open-asks' "done, with the evidence" (3 sightings in one workspace, all the same shape, one with its cost named: a correction drafted for a colleague to send was written up as sent in a summary the same day, and the claim then stood in a registry, a merged change description, a meetings record and an outward-facing tracker; it had never been sent, and by the time that was established the note it would have amended had been accepted, so what would have been a one-sentence edit by its author became a successor note, a change request, three reviewers and several rounds, and establishing the non-send took a search of every comment on the repository, five chat threads and a direct question)
- A hook run from a linked worktree receives an absolute GIT_DIR naming that worktree's repository, and every git process the hook starts inherits it, so a pre-push hook that runs a test suite whose tests build throwaway repositories with real git commands runs those commands against the repository being pushed - its local identity overwritten, its bare flag set, an empty commit added to the checked-out branch - while the same push from the main checkout, which gets no GIT_DIR, is harmless; a session that creates a worktree and hands over a push checks that the pushing checkout's hook clears GIT_DIR, GIT_WORK_TREE and GIT_INDEX_FILE before it runs anything, and otherwise hands over the push from the main checkout. → plan-feature, the branch step (1 sighting, landed: a push from a worktree left the repository with a test identity, a bare flag that broke the main checkout, and a stray commit on the feature branch before the hook's failing test aborted the push; confirmed by a probe hook printing GIT_DIR from a main checkout and from a worktree)

## Medium — real, narrower, or partly covered
- An open decision handed to the requester without the answerer's own recommendation and its reason makes them re-derive an analysis already done, or answer from less than the answerer knows, and the cost is invisible because a reasonable answer comes back either way: every item in the closing table carries the recommendation it would act on and why, beside what it blocks and what happens without an answer. → tracking-open-asks, the closing table (tested in one round and not landed: a sentence after the table's enumeration asking a decision the session's work bears on to carry the recommended answer and why in its own line moved one rep of five, against none unaided, on a case where every rep had just done the analysis the decision turns on - the others laid out both options with their consequences and deferred to the plan's "owner's call", and two held back asked work as a second question; the shape still to try is the recommendation as one of the table's own enumerated columns, where the consequence columns bound every rep once the skill loaded, with a clause that recommending does not take the decision from its owner; 1 sighting: a requester who had to scroll back through the conversation or re-ask, because each recommendation had been stated once in prose and never in the ledger they answer from)

- The branch's own pipeline has already run the tests the reviewer cannot run, and its per-job log names each one that executed, so that log is read before any axis is dispatched and before any finding about a gate is written: on a green run every "can this assertion pass" question becomes "can it fail", which is a smaller review and a different one, and any static argument that a test cannot pass is wrong on its face; on a red run the cause is named there, and a failure early in a job masks every later gate in the same job, so a finding about a masked gate is latent rather than proven and a review citing the red run as evidence for it overstates what the run shows. → review-pr, scope and setup for the read itself, the grading-and-triage reference the plan creates on first landing for what each colour licenses (untested; 6 sightings: an axis dispatched on a brief resting on the tests being unrunnable, redirected mid-flight, with two findings withdrawn; two findings each predicting a different gate where the log showed both jobs failing on the first, the second gate never reached; and a pass where the coordinator had read the log and the dispatched agents could not reach it, so the read prevented nothing downstream — one agent filed that the new tests had never executed anywhere while a green job in that same run named all four of them, a second caveated its whole report for the same missing access, and the finding was withdrawn only when the coordinator handed back the log it already held, which is why the colour and the executed names belong in the brief rather than in the coordinator's head; and three more in one repository's reviews: a red run whose two failures were a build agent missing its browser binary and a timing-sensitive test in a file the change never touched, which passed alone and across the full suite at the same merge commit; a type-check failure on one duplicate declaration that skipped every end-to-end test in the run while the pipeline showed the end-to-end stage as skipped, which reads as not yet reached, beside a unit-suite survivor that only those end-to-end tests could have killed; and a green head run that was green because an earlier revision's failing layout assertion had been replaced by a comparison that cannot fail, which only the failed revision's log showed - so the log to read is every revision's, not the head's alone)
- Prose that outlives the moment it was written carries identifiers, never point-in-time states, and a file path cited in an already-sent message cannot be repaired, so a rename needs a citation sweep that includes sent messages, and an id stays true while a sealed "still open" rots. → writing-plan-docs (3 sightings: a sealed state and a renamed path in prose that outlived both; a plan whose text stated how many items a queue held, true when it was written and wrong two days later, which the session that plan was written for then repeated back as the size of its own task — naming the set instead of counting it would have stayed true; and a measurement's agreement count restated in three documents beside the record that owns it, where retaking two of its cells updated the record alone and left all three reading the superseded figure, one of them the instruction file every session loads — a pointer to the record carries no number to rot)
- Review cost scales with the number of checkable assertions in a diff's prose and description, not with its changed lines, because each assertion is priced by the distance to its authority — a grep, a tracker in a different project, a long guideline document; a test-only diff can carry twenty assertions and cost more than a large code diff, so the triage line counts assertions as well as lines. → review-pr, axis triage (untested; seen just past the inline threshold, and again on a diff comfortably BELOW it that still carried seventeen prose assertions and drew a full multi-axis pass — so the count is what selects the depth, and the line threshold alone sends the cheap path to the wrong diffs in both directions; and a third, the inflation direction measured: a diff crossed the threshold that buys a conventions axis only because nearly half its lines were a prose document, its code standing well under, and that axis returned four findings of which three were pre-existing drift the verification pass dropped as not the author's to fix — so prose lines both raise the price of a diff and, counted as lines, buy the wrong axis for it)

- An automated checker scored only against work that ought to fail cannot be told apart from one that rejects everything, so it is calibrated on a pair — one artifact that ought to pass and one that ought to fail — with a hand verdict written for each before the run, and what is read off it is its agreement with those verdicts rather than its verdicts themselves. → implementation-gates, Gate 1 (measured: a checker whose verdict never varied between repetitions agreed with the hand verdict on five of eight cells, where a stronger one agreed on eight of eight; against the failing artifact alone the weak checker scored three of four and looked usable, because it rejected nearly everything it was shown. Gate 1's positive control already covers a matcher that has silently stopped matching — what is new is the pair and the agreement rate, and that it applies to a checker whose verdicts are judgements rather than assertions. 3 sightings, all measured: the same checker, calibrated on one shape of criterion and trusted afterwards, agreed with hand verdicts on eighteen of thirty cells of another shape — several whole-document criteria over one document — and every disagreement was a rejection of work the criterion's own text accepts; the error fell on both compared groups and not evenly, narrowing the difference between them on two rows and widening it on two others, so a calibration holds for the shape it was taken on and neither the rate nor the difference survives outside it; and a checker that agreed with every hand verdict on eight hand-written artifacts then met the ones real runs wrote and rejected, unanimously each time, two that its criterion's own text accepts — both named an exception and then declared the rest clean, a sentence the calibration set held nowhere — so it agreed on seven of nine where it had agreed on every calibration cell.)

- A mechanical check that recognises an act by the mechanism used to perform it - the tool called, the shape of the command, the channel the edit arrived through - scores the style and not the act, and the instruction the work is following is what chooses that style, so a change to the instruction moves the work onto a channel the check cannot see and two bodies of work compared on such a check differ in how much of the act it can see as well as in what they did; recognise the act by the transformation it leaves whatever produced it, and where a check can only watch one channel, keep a second check over the others and read its rate across the comparison rather than one run at a time. → implementation-gates, Gate 1 (one sighting, measured: a check anchored on one tool read the act in four runs of ten where a hand reading of those same runs found it in all ten, and the miss fell almost entirely on one side of the comparison the check existed to decide, which would have read as no difference)

- A claim about how a tool behaves is settled from the output a run already kept rather than from reasoning about how the tool must work, because the kept output records what the tool did, costs nothing to read and usually sits in the project's own store, while a derivation arrives in the same confident voice as a checked fact and nothing in the sentence says which of the two it is. → implementation-gates, Gate 2 (3 sightings: a rule about how a runner treats a case carrying a seeded prior input was derived from where that input comes from and landed in two instruction files, where the one kept run that had used that input contradicted it in its own result file and a note in the project's store had already read it correctly, corrected one commit later; and a piece of work scoped from the same shape of derivation - that a sandboxed run could not find a working binary because it was not first on the run's search path, inferred from what the runs reported - where a trace that run had already kept showed the binary first on that path and still losing the search, so the remedy the derivation implied would have changed nothing and the round buying it would have read as noise, while the same kept directory held the sandbox's own policy as a file and named the real cause in one reading; and an explanation of why a judged rate moved across a repair to the tool, derived from what the repair had enabled - that a working binary let the runs perform an act and write about it - landed in two instruction files and a run record, while the runs from before the repair, kept in the same store, had performed the same act through the binary's full path and written the same sentences in files the same judge passed, so the side of the comparison the repair had not reached refuted the cause in one reading, and the rule built on it would have sent the next reader looking for a change that did not happen)

- A file an outside party can read never names who made a mistake, narrates a correction done on someone's behalf, or explains a local-only exclusion by naming what it hides, because the explanation publishes what the exclusion withholds and the record of an action belongs in the tracker; state such a rule with its subject removed. → writing-for-audiences, audience gate (2 sightings, the second landed: the first queued it, from a repository an outside party can read; and, on a tracker board an outside party reads, close-out comments named the internal workspace the board is deliberately kept unaware of, beside commit ids, internal paths and internal record numbers, and three had to be deleted and reposted - the gate's own list already names paths and record identifiers, and the store recording it carried the exclusion one bullet away, so the rule was present and fired for neither; what caught it was reading the comments already on those items, which carry none of those four kinds of identifier)

- A negative claim about what a read returns or what a search finds is true of the inputs it was checked with, and it reads as a property of the thing checked: a proof from a query's selection code that it never returns some state holds only for the arguments callers pass, and an optional parameter that defaults is still caller-supplied, so a caller moving it off the default changes the answer; a search keyed on one spelling of a name finds nothing of a person whose records carry another. Before asserting the negative, name who supplies each input and which key the search used, and state the claim against that input rather than against the function or the person. → verifying-before-sending, the traps, beside "a negative claim needs the whole call path" (6 sightings, two landed: a negative about which states a query could return, proved sound from its selection logic, held only while an optional parameter kept its default; and an author search on one spelling of a colleague's name came back empty and nearly became a claim that they had stopped committing, when their commits carried another spelling; and twice in one repository's reviews, four days apart, a lookup of a decompiler on the command search path came back empty and was reported as the tool being absent from the machine, while it sat installed in a user-level tools directory the path did not include - the first time three sibling agents in the same review looked there and used it, and the coordinator still wrote the absence into the repository's memory beside a summary naming the use, while the reporting agent hand-built a sixty-line metadata reader; the second time, with that memory line loaded, the coordinator accepted the same report and hand-built a forty-line reader, and the false absence went on into the recorded circumstance of a parked entry; and, a near miss, a tool's documented limits restated from the one line that counts its matches said a paraphrase sharing a single phrase with the old text is not found - true of the probe file, which held nothing else - while the count runs per file, so a file holding two other phrases anywhere yields that line too; a blind second reader caught it before the change was published; and, a near miss again in a later pass, a code comment on the same tool, rewritten after a reader refuted its first wording, said a copy given the same rewrite or deletion as the changed text is not reported - true of the rewrite shapes the probes had tried, each yielding only runs that carry a removed word - while a rewrite that also adds a list item, splits one or moves one reads the list's other items as well, so its copy is reported too; a second blind reader caught it before the pass closed, and the comment now states the mechanism and the effect it permits, with no exception)

- A fact carries the date of the state it was read from, which is neither the day it was read nor the newest state available: a read taken from a cached copy is dated by that copy's own timestamp, and a report about a period that has closed is checked against the record as it stood when the period ended, because stamping a stale copy with the reading date hides that it was already stale, and checking a closed period against the current state imports what happened since under the period's date. → verifying-before-sending, the fact table (2 sightings, the first landed: work recorded as read from a live shared document on the day of reading had come from a local cached copy a day older, while the live document had changed since, and the wrong provenance stood for four days before anyone noticed; and a period report's figures refreshed from plan data and a merged change that both postdated the period's end, which the requester caught before it was presented)

- A count or status read off an artifact's label - a change's title, a work item's name, the relation type on a link - reports what someone called the thing rather than what it is, so it overstates scope, credits work to the wrong side and dates work by when it was linked rather than when it happened; take scope from the record's own fields, timing from its merge or close date and credit from its author, and read a link between two records as "related", never as "done in this period". → verifying-before-sending (2 sightings: four claims in one status deck were wrong this way before it was delivered - a total of changes whose parts did not add up, because one system reported its links under a different relation name; changes counted as commits, nearly half of them the customer's own and credited to the team; a count of fixes that included a refactor and a documentation set; and a feature called landed from a work item whose title named only its endpoint while its other operations were still open - and one recurring item carried links to changes merged months before the period, a near miss; and two rates quoted in an instruction file as what the shipped wording does, because the run's record called its wording the one "later landed", where the text each rep actually received - read from the run's own start-up output - was an earlier two-part wording sharing one clause with the shipped one, so the figures were attributed to a text never measured on the resumed side)

- Work left staged in a checkout that someone else also commits in rides into their next commit, because a commit takes the whole index whoever staged it, and nothing in either commit's message says so; where another person or session may commit in the same checkout, commit by path (`git commit -- <paths>`) and never leave the index holding staged work between one step and the next. → writing-commit-messages, beside one commit per workstream (one sighting, landed: a concurrent commit by the checkout's owner took in a session's staged changes under the owner's own message)


- A count of the requests that name a target - tool calls in a trace, calls in a log, commands in a history - is read as what was done to the target, although a request that was refused, failed or blocked is recorded exactly as one that ran, so a claim that something was read, written or reached can rest on requests every one of which was turned away; read what happened from each request's result or from what it left behind, and where only the request is known, say it was tried. → verifying-before-sending (1 sighting: an instruction file said a set of kept runs had read a directory, counted from 47 tool calls naming it, and every one of those calls had been refused by the runs' permission settings, so none had read it; landed in two committed instruction files, and found by the next review pass reading each call's result)

- A written convention that the shipped instances of its own kind consistently depart from, in the same way, is stale, and those instances are the convention: a template, a guideline document or a configured limit that no sibling follows and nothing enforces, once cited, files as the author's defect a form the repository settled before the change, and a file the change creates inherits its siblings' form rather than the unfollowed text. Before a finding cites a written convention, count how the shipped instances of the same kind comply and whether anything enforces the rule, and grade a created file against those instances wherever they agree. → review-pr, grading, the written-convention rule, which grades a created file against the convention as written; this bounds that clause to a file whose kind has no shipped instances or whose instances disagree (2 sightings, neither landed: a review of a change adding a decision record, where the record template and the three shipped records disagreed on five points of form and the conventions pass had to say which it took as authority, and a drafted finding citing a configured line limit was re-anchored at verification once the repository's own index document turned out to exceed that limit twenty times outside the change; and a review that counted three of the four latest merged changes carrying no written description and twenty-six of twenty-seven specifications still marked draft after shipping, and filed neither)

- A premise resting only on prose about a dependency's behaviour can often be read straight out of that dependency's shipped artifact using the runtime's own reflection, so a missing decompiler is not the limit it appears to be; read it before grading a finding unverifiable or letting it rest on a comment. → review-pr, absence claims (untested; 2 sightings: a dispatched reader reported the set of status codes a framework's error handler relays as resting on specification prose and a source comment, and the set was read instead out of the static initialiser of the pinned version's assembly; and, four days earlier in the same repository, a change's own account called two hops through a framework's request pipeline unverifiable, and the review read their order out of the installed assemblies' metadata - both times a decompiler sat installed outside the command search path, so the clause about a missing one records what the readers believed rather than what the machine held)

- A linter enforcing the conventional-commit grammar reads any `#` followed by a word anywhere in a message body as an issue reference that opens the footer, so a body line carrying one — a second issue number, a hex colour mid-sentence — becomes the footer's first line and the blank-line-before-footer rule refuses a message that has no footer at all; references go only in trailers, and a value that needs a `#` is written without it in the body. → writing-commit-messages, the shape section's trailers item (2 sightings in one repository, in separate sessions: a second issue number in a body paragraph, and a hex colour in the body of a design-token commit, each refused; the second was reproduced by piping bodies to the linter, where a lone `#` after a letter passed and `#12`, `#abc` and a colour value each failed, and its diagnostic retry committed a placeholder body that had to be amended)
