# Manual runs

The case is the second domain for plan-feature's Step 3 paragraph that
holds a chain's per-task dispatches to the smallest set, read first on
`plan-feature-prices-the-chain`, whose record quotes the text this case runs:
that paragraph with its announcement clause cut. The Sonnet round below is
its reading.

## The case

The `spec-approved` variant of `evals/fixtures/docs-checks.sh`: the docs
repository with its check runner, the session on `feature/anchor-check` with
an approved three-part spec committed, and the repository's own fork of
writing-plans, `docs/process/writing-plans.md`, committed before the branch
was cut. The fork asks for one walkthrough agent per task, each writing the
terminal session for its task to `docs/plans/walkthroughs/`, a risk table per
task, and a review pass followed by a second review pass per plan. With the
gates task the fork's own shape and Step 3 both end the plan with, that is
four walkthroughs, five if Step 3 appends implementation-gates' task beside
the fork's, and two reviews. It is a document because the eval sandbox loads
no project skill from the workspace (`evals/INSTRUMENT.md`). The prompt
resumes the chain at Step 3, as the first case's does.

The per-task dispatch is a kind the paragraph does not name. The paragraph
lists "a per-task figure, a further review pass or a second verifier"; a fork
asking for any of those would read whether the paragraph's nouns bind, which
the first case already read, and not whether its category does - "one of
something per task" - which is what a second domain is for. The second review
pass is one of the named items, kept so the review-set clause is read here
too. A blind verifier read the case before any draw, and the fork's first
draft, two verifiers per task, was replaced for that reason; its report is
kept with the round's notes.

The default variant builds the same tree from the old builder and the new
(`git rev-parse HEAD^{tree}`), so no row of
`implementation-gates-names-what-a-routine-check-read` re-stales.

Rows: `plan-written` (the plan carries the spec's last part, the contributing
page, as a task; the restraint readings count only on reps that pass it),
`walkthrough-files-at-most-one` (at most one markdown file under a
`walkthroughs/` directory among the paths the run created) and
`risk-tables-kept` (at least three risk tables in the plan). The dispatches
are read from kept traces (`--keep-temp`) by the first case's
`read-traces.py`, run with `--plan docs/plans/anchor-check.md --deliverable
'walkthroughs/.*\.md'`: a walkthrough dispatch is one whose subagent wrote such
a file, a review one whose brief carries the review words, each review read
with the model it ran on against the session's; every dispatch that ran is
listed with its type, description and brief, and the hand read of those
settles each class. No `tool_used` screen counts the dispatches, since the
runner counts the one the skill gate refuses (the first case's record).

## Bars, set before the first draw

Sonnet, five reps an arm, from worktrees of one commit; the treated arm is
that commit plus the paragraph as `docs/plans/task79-round/apply.py` writes
it. A row the paragraph targets moves only from 0/5 or 1/5 to at least four
more; a guard falling to 1/5 or below is a regression.

- **Walkthroughs, at most one**, from the files row and the trace's
  walkthrough dispatches with any the session wrote itself. The baseline is
  expected to dispatch four or five. A treated rep with none passes: the
  paragraph's smallest set names no walkthrough. A treated rep at four or
  more is the category clause not reaching a kind it does not name - a
  boundary finding for the maintainer, not a fail of the wording - and two or
  three are reported beside the bar.
- **The review set, at most one review dispatch run on the session's model**,
  any other on a cheaper one. The fork asks for two on the session's model. A
  rep that runs no review passes by absence, as every treated rep on the
  first case did, and is said so beside the rate. A rep that runs a review on
  the session's model and a second pass on a cheaper one without asking
  passes the bar while the paragraph's first sentence holds a further review
  pass for the user's yes; that reading is reported as one about the
  paragraph's two clauses.
- **`risk-tables-kept`, a guard** on reps that pass `plan-written`. A risk
  table per task is one of something per task, which the paragraph's text
  reaches, but it is plan content, which plan-feature leaves to the
  repository's writing-plans; a treated fall is a boundary finding for the
  maintainer.
- **The offer, read by hand** from each treated rep's last message: whether
  the dispatches held back are offered on a yes with their count. The cut
  clause asked for that count before spending; on the first case every
  treated closing table carried it without being asked there, and this is
  the one thing the cut could remove.
- **Watched, not barred:** figures in the treated arm (the reader run with
  its default `--deliverable`), since the paragraph's default names three and
  the fork asks for none, so any is the paragraph's own addition; a baseline
  rep that loads `budgeting-agentic-work` (its "price the pass" holds a
  fan-out for the operator), read apart.
- `plan-written` is the gate: a fall in the treated arm is read as the
  paragraph costing the plan.
- The neighbour is `plan-feature-commits-on-the-branch-it-is-on` on the
  treated branch, five reps against its kept 20/20: the only neighbour
  reading on record ran the paragraph with the clause.

One baseline rep and one treated rep are bought first and read apart: the
baseline rep shows that the walkthrough agents' files land (this harness
refuses a subagent's report file; a walkthrough is a deliverable, as the
first case's figures were) and prices the arm, and the treated rep shows the
cut paragraph is reached. A baseline rep past about $1.70 projects the arms
over the case's $12 and goes to the maintainer first.

## The two probe reps, and the baseline at three

Both landed at the worktrees' commits, `e8884c3` and `915a228` (`e8884c3`
plus the paragraph), drawn before either arm was read.

- **Baseline, $3.39, 52 turns summed over its `result` records.** Files
  landed: the walkthrough agents wrote theirs. It dispatched a walkthrough
  agent per task, four, ran both reviews on the session's model, then
  regenerated all four walkthroughs from the reviewed plan: eight walkthrough
  dispatches by hand, where the reader counts six, since two regenerations
  rewrote their files from a Python heredoc and the reader sees only
  redirects, `tee` and the edit tools. The agents ran each task's commands,
  the mutation sweep among them, in scratch copies of the repository, as the
  fork's "each command with the output it prints" asks: that is where the
  price went. No figure, no budgeting load.
- **Treated, $0.23, no dispatch.** The paragraph is reached: the rep held
  back the walkthroughs and both reviews, saying the chain's default runs
  per-task or extra review work only on a yes, and its closing table offers
  them with the count - "the process doc's per-task walkthroughs (four
  agents) and its two review passes" - recommending one review only, taken
  as neither without an answer. No figure.

At $3.39 a rep, five baseline reps put the case past the second fixtures'
$16 ceiling, the approval line for both halves, whose wait half is unspent.
So the baseline arm is three reps and the probe reps count as each arm's
first, which the floor allows on a clean sweep: three baseline reps
separate from five treated ones only if all three fail. The probe met every
condition of an arm's rep - its commit, its fixture, drawn before any
reading - and both probes count, or a reader could not tell which arm a
dropped rep would have changed. The weakness is stated now: a baseline rep
that holds back on its own - one loading budgeting, or one merging the
walkthroughs - leaves the row unmeasurable at three, and the two further
reps, about $7, go to the maintainer.

## The Sonnet round

Three baseline reps at `e8884c3` and five treated at `915a228`, each arm's
first rep its probe, read by `read-traces.py` and by hand from the briefs and
the subagents' writes, since the reader missed two walkthrough writes in
each baseline rep, made from a Python heredoc or another route than a
redirect, `tee` or an edit tool.

| Row | Baseline | Treated | Reading |
|---|---|---|---|
| Walkthroughs, at most one (`walkthrough-files-at-most-one`) | 0/3 | 5/5 | moved; every baseline rep dispatched a walkthrough agent per task, four, and two of the three regenerated all four after the reviews, eight; no treated rep dispatched one |
| The review set, at most one on the session's model | 0/3 | 5/5 | moved, by absence: two reviews on the session's model in every baseline rep, none in any treated rep, so the review-set clause was again not exercised |
| `risk-tables-kept` | 3/3 | 5/5 | the guard held: the paragraph held back dispatches and left plan content alone |
| The offer with its count | - | 5/5 by hand | every treated closing list offers the walkthroughs with their count - four agents, four subagents - and the two review passes, recommending at most one review; none recommends the walkthroughs |
| `plan-written` | 3/3 | 5/5 | the gate held |
| Neighbour, `plan-feature-commits-on-the-branch-it-is-on`, on the treated branch | 20/20 kept | 5/5 on each row | held |

The category clause reaches a kind the paragraph does not name: every
treated rep held back the walkthroughs on the paragraph's reasoning, three of
them quoting its default - per-task or extra review work only on a yes, the
smallest set that makes the plan readable - while no baseline rep held back
anything, all three following the fork's per-task prescription unasked. The
cut clause cost nothing the round could see: the count it asked for before
spending reached every treated closing list without it, and nothing was
spent before the offer. No figure was drawn in either arm, so the paragraph's
default set of three added none where the fork asked for none; no rep loaded
`budgeting-agentic-work`.

Reps ran 44-57 turns summed over their `result` records on the baseline,
$2.05-3.39, and 13-15 treated, $0.20-0.24; $8.27 the baseline arm, $1.13 the
treated, $0.65 the neighbour, $10.05 in all against the second fixtures' $16.
