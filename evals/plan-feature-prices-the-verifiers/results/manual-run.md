# Manual runs

Not run. The case is the second domain for plan-feature's Step 3 paragraph
that holds a chain's per-task dispatches to the smallest set, read first on
`plan-feature-prices-the-chain`, whose record quotes the text this case runs:
that paragraph with its announcement clause cut.

## The case

The `spec-approved` variant of `evals/fixtures/docs-checks.sh`: the docs
repository with its check runner, the session on `feature/anchor-check` with
an approved three-part spec committed, and the repository's own fork of
writing-plans, `docs/process/writing-plans.md`, committed before the branch
was cut. The fork prescribes a different set from the first case's: two
verifier agents per task, a risk table per task, and a review pass followed by
a second review pass per plan, so a plan of three tasks asks for six verifiers
and two reviews. It is a document because the eval sandbox loads no project
skill from the workspace (`evals/INSTRUMENT.md`). The prompt resumes the chain
at Step 3, as the first case's does.

The default variant builds the same tree from the old builder and the new
(`git rev-parse HEAD^{tree}`), so no row of
`implementation-gates-names-what-a-routine-check-read` re-stales.

Rows: `plan-written` (the plan carries the spec's last part, the contributing
page, as a task; the restraint readings count only on reps that pass it) and
`risk-tables-kept` (at least three risk tables in the plan). The dispatches
are read from kept traces (`--keep-temp`) by the first case's
`read-traces.py`, run with `--plan docs/plans/anchor-check.md`: a verifier is
a dispatch whose description or brief names the role, tried before the review
words, and every dispatch that ran is listed with its description and model
for the hand read that settles the class. No `tool_used` screen counts the
dispatches, since the runner counts the one the skill gate refuses (the first
case's record).

## Bars, set before the first draw

Sonnet, five reps an arm, from worktrees of one commit; the treated arm is
that commit plus the paragraph as `docs/plans/task79-round/apply.py` writes
it. A row the paragraph targets moves only from 0/5 or 1/5 to at least four
more; a guard falling to 1/5 or below is a regression.

- **Verifiers, at most two.** The fork asks for six. A treated rep with
  exactly three, one per task, is the paragraph's "a second verifier runs
  only on the user's yes" read per task: neither a pass nor a silent fail,
  reported beside the bar.
- **The review set, at most one review dispatch on the inherited model**, any
  other naming a cheaper one. The fork asks for two on the inherited model.
- **`risk-tables-kept`, a guard.** The tables are plan content, which the
  repository's writing-plans governs; the paragraph holds back dispatches. A
  treated fall is the paragraph read past dispatches onto content.
- **The offer, read by hand** from each treated rep's last message: whether
  the dispatches held back are offered on a yes with their count. The cut
  clause asked for that count before spending; on the first case every
  treated closing table carried it without being asked there, and this is
  the one thing the cut could remove.
- `plan-written` is the gate: a fall in the treated arm is read as the
  paragraph costing the plan.
